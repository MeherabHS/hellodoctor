# Backup encryption-key custody runbook

This is an operational procedure, not a claim that a production custodian is
currently assigned. No actual custodian, production key, or secret is named or
generated by this document — see `docs/MILESTONE_8_REMAINING_GAP_ASSESSMENT.md`
(M8-G-06) for why it exists and what remains an operator decision.

## What this protects

`PGBACKREST_REPO1_CIPHER_PASS` is the single AES-256-CBC passphrase that
encrypts the entire pgBackRest repository (every full backup, differential
backup, and archived WAL segment).

**Correction (2026-11-01): an earlier version of this paragraph incorrectly
claimed the passphrase is "never written to disk in plaintext by the
application." That was wrong, and the inaccuracy is corrected here with the
exact evidence instead of restated vaguely.** It *is* written to disk in
plaintext, exactly once, by `backup-entrypoint.sh`/`postgres-entrypoint.sh`,
into `/etc/pgbackrest/pgbackrest.conf` (`repo1-cipher-pass=...`) — this is
inherent to how pgBackRest itself works, not a defect specific to this
deployment; pgBackRest has no mechanism to read the passphrase except from its
own plaintext config file. Confirmed directly in this environment, on a
disposable container with a fake test passphrase, via
`grep -c 'repo1-cipher-pass=<test-value>$' /etc/pgbackrest/pgbackrest.conf`
returning `1`. The only protection on that file is filesystem permissions
(`chmod 0640`, owned by `postgres:postgres`, directory `chmod 0750`) — not any
absence of plaintext.

**A second, separate exposure was found and partially fixed in the same
pass.** Because the passphrase was *also* passed as a plain container
environment variable (`PGBACKREST_REPO1_CIPHER_PASS` in
`deploy/single-vm/compose.backup.yml`), it was fully visible in plaintext to
`docker inspect <container>` (`.Config.Env`) and `docker exec <container> env`
— confirmed directly: both commands returned the exact fake test passphrase
value, unredacted, on a disposable container in this environment. This is a
real exposure to anyone with access to the Docker daemon/socket on the host
(any member of the host's `docker` group, or root) — a materially larger
population than "can read a 0640 file as the `postgres` user inside the
container."

**Fix applied:** both entrypoint scripts now also accept
`PGBACKREST_REPO1_CIPHER_PASS_FILE` (a path to a file containing the
passphrase, e.g. a Docker/Swarm secret mount) in preference to the plain env
var. A file path is not itself sensitive, so this removes the
`docker inspect`/`docker exec env` exposure vector entirely when used — only
`PGBACKREST_REPO1_CIPHER_PASS_FILE=/run/secrets/...` (a path) appears in
`docker inspect`/`env`, never the value. Verified directly: with only the
`_FILE` variant set, `docker inspect`/`docker exec env` showed no
`PGBACKREST_REPO1_CIPHER_PASS` key at all, while `pgbackrest.conf` was still
generated with the correct passphrase read from the file. The plain env var
remains supported, unchanged, for backward compatibility — this was additive,
tested before and after, not a change to a working mechanism without testing.
Full test detail in `docs/MILESTONE_8_BACKUP_OPERATIONS_CLOSURE.md`'s
2026-11-01 follow-up section.

**What this does *not* fix, and cannot be fixed by file permissions alone:**
anyone with root or Docker-daemon access on the host can always read a running
container's filesystem (`docker exec ... cat /etc/pgbackrest/pgbackrest.conf`,
or the file named by `_FILE`) or its mounted volumes directly, regardless of
in-container file permissions. The `_FILE` mechanism removes the *convenience*
exposure (`docker inspect`/`env` require no further access beyond what
starting the container already implied), not host-root access itself — the
real control for that is restricting who has Docker/root access on the
production host, which is an operational decision, not something this
repository's code can enforce.

**There is exactly one passphrase in the current local configuration — no key
versioning, rotation schedule, or secondary/escrow key exists yet.** This
runbook's "lost-key consequences" section exists because of that, not despite
it.

## Approved external key-storage requirements

The passphrase must live in an external secret store, never in this
repository, `.env`, a compose file, or a Docker image layer. Acceptable stores
(pick one at deployment time, do not invent a new mechanism per environment):

- A cloud secret manager (e.g. Azure Key Vault) with access-logged reads and a
  retention/soft-delete policy independent of the application's own data.
- An offline, access-controlled password manager or hardware-backed vault, for
  a purely local/pre-cloud deployment, with at least two independent copies
  stored in physically separate locations (e.g. two different secured
  locations, not two folders on the same machine).

Not acceptable: the repository, any `.env` file, a chat message, a shared
spreadsheet, or a single person's personal device with no backup copy.

## Custodian and backup-custodian roles

Two named roles, filled by two different people, must exist before this
mechanism is relied on in production (neither is named here — that is an
operator decision, recorded outside this document in whatever access-control
system the secret store provides):

- **Primary custodian** — day-to-day holder of record; the person who
  retrieves the key during a real recovery.
- **Backup custodian** — holds independent access to the same secret store
  (or an independently stored copy), used only if the primary custodian is
  unavailable, has left the organization, or their own access is itself
  compromised.

No single person should be both the only person with secret-store access and
the only person who knows the recovery procedure exists.

## Automated retrieval on routine restart (2026-11-06 follow-up)

`deploy/single-vm/backup/fetch-keyvault-secret.sh` now exists: when
`AZURE_KEY_VAULT_NAME`/`AZURE_KEY_VAULT_SECRET_NAME` are set, the container
retrieves the passphrase from Key Vault itself, via its own managed identity,
at startup — no human types or pastes it. **This does not replace anything in
this document; it narrows what it applies to.** It automates exactly one
case: *the same, already-running VM restarting its own containers*, where a
human already made the one-time decision to grant that VM's identity `Get` on
this one secret via Key Vault RBAC. Everything else here is unchanged:

- Who can grant or revoke that identity's access, and who can read or rotate
  the secret's *value* in Key Vault, is governed by Key Vault's own RBAC —
  set up and audited by a human, not by this script.
- The "VM-loss recovery" section below is untouched: a *replacement* VM has a
  different identity, which still needs a human to grant it access before
  automated retrieval works for it. The custodian roles and the manual
  procedure exist specifically for that case (and for any Key Vault outage
  or access-loss scenario), not for routine restarts of a VM that already has
  access.
- The secret's full versioned identifier (e.g.
  `https://<vault>.vault.azure.net/secrets/<name>/<version>`) — never its
  value — is written alongside each backup's recovery manifest
  (`/var/log/pgbackrest/recovery-manifest-latest.json`), so a later audit can
  state exactly which secret version produced a given backup without anyone
  having recorded the value anywhere.

This has been tested against synthetic Azure IMDS/Key Vault response shapes
and against IMDS being unreachable (the script fails loudly and clearly, as
it will on any non-Azure host); it has **not** been exercised against a real
Key Vault, real managed identity, or real RBAC grant.

## Access and recovery procedure

1. Declare the need (a real restore, a drill, or a verified loss) and record
   who requested it and why, same as the incident-declaration step in
   `docs/DISASTER_RECOVERY_PLAN.md`.
2. The primary custodian (or backup custodian, if the primary is unavailable)
   retrieves the current passphrase from the approved secret store. Record
   *that* retrieval happened (timestamp, requester, approver) in the incident
   log — never record the passphrase value itself anywhere outside the secret
   store.
3. Supply it to the recovery environment only via the same mechanism
   production uses (an environment variable injected by the secret store or
   orchestrator at container start) — never paste it into a shell history,
   ticket, chat, or file that outlives the recovery session.
4. After the recovery (or drill) completes, confirm the passphrase was not
   left in any container's environment dump, log, or temporary file on the
   recovery host.

## Key rotation considerations

**Correction (2026-11-01): there is no supported in-place passphrase
rotation. An earlier version of this section incorrectly described one
("update `PGBACKREST_REPO1_CIPHER_PASS` and restart... so new backups use
it") — that procedure does not work and must not be attempted against a real
repository.** pgBackRest fixes a repository's encryption type and passphrase
when the repository's stanza is initialized
(`pgbackrest stanza-create`); it has no command to re-key an existing
repository in place, and simply changing `repo1-cipher-pass` in config and
restarting would leave pgBackRest unable to correctly use the already-created
repository — the existing backups were encrypted with the old passphrase
tied to that repository's stanza, and pgBackRest does not re-encrypt or
migrate them when the configured passphrase changes underneath it. **Do not
attempt this against the real repository.** No actual rotation was performed
or attempted in producing this correction.

### The safe migration path: a new repository, not a changed one

pgBackRest 2.x (confirmed: the installed `pgBackRest 2.60.0` in
`deploy/single-vm/backup/pgbackrest.Dockerfile`) supports multiple
simultaneously configured repositories per stanza (`repo1`, `repo2`, ...),
each with independent type/path/cipher settings — this is the supported
mechanism for this exact situation, not a workaround. Per pgBackRest's own
`stanza-create` command help, confirmed directly against the installed
binary: *"If there is more than one repository configured, the stanza will be
created on each. Stanzas that have already been created will be skipped so it
is always safe to run stanza-create, even when a new repository has been
configured."* That is: adding a second repository and running
`stanza-create` again is explicitly documented as safe and a no-op for the
already-existing `repo1` — it will not touch or re-key it.

The procedure, to be run and verified against a **disposable** stanza/repository
before any production use, never against the real one:

1. Choose and record a new passphrase in the approved secret store as a new,
   separate entry — do not overwrite the old one's entry.
2. Add a second repository block to `pgbackrest.conf` (via the entrypoint
   scripts' config generation, extended to also emit `repo2-*` settings) —
   same `repo1-type`/`repo1-cipher-type` shape, but a different
   `repo2-path` (or a different Azure container, once Azure is available) and
   the *new* passphrase as `repo2-cipher-pass`.
3. Run `pgbackrest --stanza=<stanza> stanza-create` — per the help text
   above, this is safe to run again; it only acts on the not-yet-created
   `repo2`.
4. Run a full backup specifically targeting the new repository:
   `pgbackrest --stanza=<stanza> --repo=2 --type=full backup`.
5. Verify the new repository independently (`pgbackrest --repo=2 check`,
   `--repo=2 info`, and ideally a disposable restore drill from `--repo=2`,
   the same class of drill already proven for `repo1` in
   `docs/recovery-evidence/m8-final-local-dr/`) before relying on it.
6. Only once step 5 passes: reconfigure scheduled backups
   (`backup-runner.sh`) to target `--repo=2` going forward (or renumber
   repositories, per pgBackRest's own renumbering support, so the new one
   becomes `repo1` — a separate, also-must-be-tested-first step).
7. **Keep the old repository and its old passphrase, unchanged, in both the
   repository storage and the secret store**, for at least as long as the
   longest-retained backup set it holds (today: 7 full-generation retention,
   `docs/BACKUP_RESTORE_RUNBOOK.md`'s retention table) — a restore request for
   a point in time before the migration can only be served from the old
   repository with the old passphrase.
8. Only remove the old repository and retire its passphrase from the secret
   store after confirming, by actually checking `pgbackrest info` against it,
   that no backup/WAL segment still needed for the approved retention/RPO
   window depends on it.

This has **not** been performed against any real repository in this
environment — producing and verifying it against a disposable repository
(steps 1-5 above, with synthetic data) is listed as a remaining operator
action, not claimed as done here. Rotation remains a manual, rare,
deliberately-reviewed procedure, not something to schedule routinely.

## VM-loss recovery

The passphrase lives only in the secret store and the (lost) VM's environment
— never in the repository or the backup volume itself. A VM loss therefore
does **not** lose the key: the custodian retrieves it from the secret store
exactly as in the "Access and recovery procedure" above and supplies it to the
replacement VM's `backup`/`postgres` containers. This is the one scenario this
mechanism is specifically designed to survive; it is the *secret store's* own
loss or the *custodians'* own loss of access that this runbook otherwise
guards against.

## Lost-key consequences

If the passphrase is genuinely unrecoverable (both custodians' access is lost,
and the secret store's own copy is also lost or destroyed): **every encrypted
backup and archived WAL segment in the repository becomes permanently
unreadable.** pgBackRest cannot recover, brute-force, or bypass the cipher.
This is identical to the documented outcome in
`docs/DISASTER_RECOVERY_PLAN.md`'s "Lost encryption key" row
("do not claim object recovery... otherwise encrypted data remains
unreadable"). The only mitigation is prevention: the two-custodian,
multi-location storage requirement above exists specifically so that no single
point of failure can cause this outcome.

## Tabletop recovery test

Run this as a drill, with no production key or real custodian names involved,
to validate the *procedure* rather than the actual secret:

1. Using a disposable, clearly-labeled test passphrase (never a real one),
   simulate "primary custodian unavailable" and have whoever is standing in
   for the backup-custodian role retrieve the test passphrase from a
   disposable instance of the same class of secret store.
2. Time how long retrieval plus approval actually takes, end to end, and
   record it — this is the real-world floor on the DB recovery RTO
   (`docs/DISASTER_RECOVERY_PLAN.md`: ≤4 hours), not the pgBackRest mechanics
   alone.
3. Confirm the retrieved value was never written to a durable log, ticket, or
   chat transcript during the drill.
4. Record gaps found (e.g., the backup custodian's access was stale, the
   retrieval process was undocumented, approval took too long) the same way a
   DR drill records gaps, per `docs/DISASTER_RECOVERY_PLAN.md`'s "Operational
   schedule" section.

This drill has **not** been run in this environment — doing so requires
naming real custodians and provisioning a real secret store, both of which are
operator decisions outside the scope of this document. See
`docs/MILESTONE_8_BACKUP_OPERATIONS_CLOSURE.md` for what was and was not
exercised locally.
