## 1. Inventory and method

Real traffic was generated by the project's own documented 1,200-session
REALISTIC_RAMP profile (`capacity_test.rs`, 120s ramp, 300s duration) against
Configuration A, with `pg_stat_statements` reset immediately before each
measurement run so every number below is attributable to that run alone.
This workload exercises: authentication/session validation, doctor
discovery, slot availability, booking/payment/webhook confirmation,
chat messaging, consultation telemetry, admin monitoring, and the
`notification_scheduler` background maintenance loop (chat-lock expiry,
consultation-trace cleanup, T-15 appointment reminders) — it does not
generate traffic against CMS/articles/MCQs, FCM device registration, or
admin reporting beyond telemetry; those are marked NOT MEASURED below,
not silently assumed fine.

For every candidate, the live query plan was inspected with
`EXPLAIN (ANALYZE, BUFFERS)` against the real, restricted application role
(`hellodoctor_api` / `hellodoctor_system_worker`, via `SET ROLE`) and real
session GUCs, using real seeded data. Mutating statements were tested inside
`BEGIN; ...; ROLLBACK;`. Candidate indexes were tested *before* being written
into a migration, by creating them inside a rolled-back transaction and
re-running the same `EXPLAIN`, so "would this actually change the plan" was
answered empirically, not assumed.

## 3. Why most of the 60 "unindexed foreign keys" are not bugs

A static scan (`pg_constraint` joined against `pg_index`) found 60 single-
column foreign keys with no leading-column index anywhere in the schema.
Per the explicit instruction not to index every FK reflexively: each was
reasoned about, not blanket-flagged. The two that turned out to matter
(`appointments.slot_id`, and the `chat_conversations`/`doctor_schedule_slots`
pair already covered above) were found because real, representative traffic
actually hit them expensively — not because they appeared on this list. The
remaining ~57 are overwhelmingly: (a) low-frequency admin/audit columns
(`approved_by`, `finalized_by`, `acknowledged_by`, `created_by` on
financial/CMS tables), (b) columns on tables too small for an index to
matter (`notification_templates`, `platform_payment_methods`), or (c)
columns not actually used as a direct query filter anywhere in the
application (confirmed by searching `src/` for `WHERE <column>` usage before
concluding "no change justified" rather than assuming). None were observed
costing meaningful time in the real workload measured here.

Identical pass/fail/ignored count at every stage — **zero regressions**
across the entire batch of changes. `cargo fmt --check` and
`cargo clippy --all-targets -- -D warnings` clean throughout (only one
Rust source line changed: the chat-lock discovery query string).

**Write-performance and storage impact**: the two new indexes
(`idx_slots_start_time`, `idx_appointments_slot_id`) are plain, non-partial,
and maintained on every INSERT/UPDATE touching `start_time`/`slot_id` — both
values are set once at row creation and never updated for these tables in
this codebase, so there is no update-amplification, only the one-time
insert-time cost of a btree maintenance operation (routine, not measured
separately as negligible for tables this size). The partial index
(`idx_chat_conversations_expiry_unlocked`) only grows during a
conversation's active (unlocked) lifetime and shrinks permanently once
locked, bounding its long-term size to the "currently open" subset, not the
whole table. No duplicate or redundant index was created — each was checked
against the existing index list (`\d` output) before being added.

**No unauthorized access introduced**: the focused test suites specifically
exercise cross-account denial (BOLA), sender-identity spoofing denial, and
RLS-scoped trace access for every one of the three changes; all pass with
every change applied simultaneously (the final regression run included all
three migrations).

**Migration discipline**: each migration was forward/down/forward
round-trip tested on a disposable, throwaway Postgres 16 container (created
and destroyed for this purpose only) before being applied to any shared
development database. No previously-applied migration file was modified or
renamed.

### 5.2 Maintenance-job volatile-timestamp scans (migration `20261202000004`)

**Original**: `cleanup_consultation_trace(p_limit)`'s discovery SELECT —
```sql
SELECT e.id,e.appointment_id FROM consultation_trace_events e WHERE e.expires_at<=clock_timestamp()
AND NOT EXISTS(SELECT 1 FROM consultation_trace_holds h WHERE h.appointment_id=e.appointment_id AND h.release_at IS NULL)
ORDER BY e.expires_at,e.id LIMIT 500
```
**Original plan**: `Index Scan using consultation_trace_expiry` used purely
to serve `ORDER BY`, with `expires_at<=clock_timestamp()` as a post-scan
`Filter` (not an `Index Cond`) — "Rows Removed by Filter: 63686" (the entire
table). 43,818 buffers, 26.653ms.

**Identified inefficiency**: `clock_timestamp()` is VOLATILE; PostgreSQL
cannot fold it to a constant at plan time, so it falls back to a generic
~33% default selectivity guess (`rows=21229` estimated against 0 actual) —
exactly 63,686 × ⅓ — rather than consulting the real `expires_at` histogram,
and chooses a scan-and-filter strategy that degrades to a full index scan
when the true match rate is near zero.

**Fix**: `clock_timestamp()` → `now()` in this SELECT only (the per-row
`DELETE ... WHERE id=r.id AND expires_at<=clock_timestamp()` safety recheck,
and the chat-lock `UPDATE ... SET locked_at=clock_timestamp()` audit
timestamp, both correctly keep volatile "truly now" semantics — only
discovery-phase comparisons changed).

**New plan**: `Index Cond: (expires_at <= now())` — a true bounded index
range scan. 11 buffers (hit), 0.124ms.

**Before/after**: 43,818 → 11 buffers (~3,983x); 26.653ms → 0.124ms (~215x).
Live on Configuration A (reset `pg_stat_statements` before/after): 23.254ms
mean → 0.023ms mean (46 calls → 7 calls observed in the shorter final-run
window, consistent with near-zero real cleanup backlog in this synthetic
dataset — the point is the *per-call* cost, which is what changed).

**Original**: chat-lock discovery SELECT (`consultation_trace.rs::maintenance`) —
```sql
SELECT id,appointment_id FROM chat_conversations WHERE NOT is_locked AND expires_at<=clock_timestamp() ORDER BY expires_at LIMIT 100 FOR UPDATE SKIP LOCKED
```
**Original plan**: `Seq Scan on chat_conversations` (no index existed at
all) — 387 buffers, 2.475ms. Already the only sound plan given no index, so
not pathological the same way as above, but a cost that scales linearly
with table size, in a job that runs every 60 seconds forever.

**Identified inefficiency**: missing index; confirmed (not assumed) that
adding the index *alone*, without also fixing the volatile-timestamp
issue, makes this *worse* (3.554ms / 9,251 buffers — same per-row-filter
pathology as above, now walking the new, smaller index instead of the
table).

**Fix**: new partial index `(expires_at) WHERE NOT is_locked`, **and**
`clock_timestamp()` → `now()` in the same statement (Rust source edit,
`services/consultation_trace.rs`).

**New plan**: `Index Cond: (expires_at <= now())`, `Filter: (NOT is_locked)`
— 2 buffers, 0.014ms.

**Before/after**: 387 → 2 buffers (~194x); 2.475ms → 0.014ms (~177x). Live:
2.475ms mean → 0.011ms mean.

**PostgreSQL CPU/memory**: not separately attributable to this specific
fix in isolation (it is one of several queries in a 60-second-interval job
whose aggregate cost is small relative to the dominant `consultation_sessions`
monitor query, §5.4) — its contribution to overall Postgres CPU was already
small in this 300-second benchmark window, but its *absolute* cost reduction
(≥99.5% per call) compounds materially over the job's actual production
lifetime (every 60 seconds, forever, against an ever-growing table), which a
5-minute benchmark cannot fully represent — disclosed rather than overstated.

### 5.3 T-15 reminder scan indexes (migration `20261202000005`)

**Original**:
```sql
SELECT a.id AS appointment_id, d.user_id AS doctor_user_id, du.preferred_language AS doctor_language,
       COALESCE(p.user_id, g.user_id) AS patient_user_id,
       COALESCE(pu.preferred_language, gu.preferred_language) AS patient_language, s.start_time
FROM appointments a JOIN doctor_schedule_slots s ON s.id = a.slot_id
JOIN doctor_profiles d ON d.id = a.doctor_id JOIN users du ON du.id = d.user_id
JOIN patient_profiles p ON p.id = a.patient_id
LEFT JOIN patient_profiles g ON g.id = p.guardian_patient_id
LEFT JOIN users pu ON pu.id = p.user_id LEFT JOIN users gu ON gu.id = g.user_id
WHERE a.status IN ('CONFIRMED','WAITING') AND s.start_time > $1 AND s.start_time <= $2
```
(parameters are plain bound `DateTime<Utc>` values computed once in Rust —
not a volatile-function issue this time, a pure missing-index case.)

**Original plan**: `Hash Join` of two `Seq Scan`s — `appointments`
(11,186 of 24,626 rows match `status IN (...)`, 333 buffers) and
`doctor_schedule_slots` (0 of 62,400 rows match the 15-minute window, but
731 buffers spent finding that out — no index on `start_time` existed at
all). 1,064 buffers total, 7.579ms.

**Identified inefficiency**: two missing single-column indexes
(`doctor_schedule_slots.start_time` has no plain/global index — only the
doctor-scoped `idx_slots_doctor_date(doctor_id,start_time)`, useless for a
cross-doctor scan; `appointments.slot_id` has no index despite being a
foreign key).

**Tested incrementally, not assumed**: adding only `doctor_schedule_slots
(start_time)` dropped the slots side to an index scan (335 buffers,
1.465ms) but left `appointments` as the new dominant Seq Scan cost (333 of
335 buffers). Adding `appointments(slot_id)` as well let the planner flip
to an all-index-driven nested loop, since the slots side is now the tiny
driving set.

**New plan**: Index Scan on `idx_slots_start_time` (driving, ~5 rows
estimated) → Index Scan on `idx_appointments_slot_id` (probed per matching
slot) → PK index scans for every remaining join. No sequential scan
anywhere in the plan. 2 buffers, 0.184ms.

**Before/after**: 1,064 → 2 buffers (~532x); 7.579ms → 0.184ms (~41x).

### 5.4 Admin consultation monitor — confirmed already optimal, not changed

Full detail in `docs/MILESTONE_8_0_PERFORMANCE_CHARACTERIZATION.md` §(the
consultation_sessions analysis). Restated here for completeness of this
audit's table: `WHERE status IN (3 values) OR recovery_state = 'NEEDS_REVIEW'`
matches 48.2% of a 23,877-row table — far too non-selective for any index to
help — and PostgreSQL already chooses a Seq Scan + top-N heapsort (17.3ms,
484 buffers), the only sound plan for this shape. Its 30-38% share of total
query time across every measurement in this pass is pure call-volume (938-
974 calls per 300s from admin-telemetry polling), not per-call inefficiency.
**No index was added.** If this polling frequency itself is a concern, that
is an application-level (caching/poll-interval) question, outside an
index/query-shape audit's scope.

## 6. Integration with Milestone 8 — steady-state, not synthetic-number chasing

All three fixes were measured against the **same REALISTIC_RAMP profile**
used throughout Milestone 8.0 (1,200 sessions, 120s ramp, 300s duration),
never SIMULTANEOUS_BURST (retained separately as the explicit stress-test
profile, unchanged). No database behavior was altered to chase a higher RPS
number — every change here targets query *efficiency* (buffers/latency per
call), and the achieved RPS in every run (85-91 req/s) was consistent
regardless of these fixes, because it is governed by the harness's
think-time parameters, not database speed.

**Overall PostgreSQL CPU did not drop further between the chat-only fix and
the final (all-three-fixes) measurement (15-18% in both)** — disclosed
plainly rather than claimed as an additional win it is not: the two
maintenance-job queries and the T-15 reminder query were already a small
fraction of the 300-second benchmark's *aggregate* CPU time (their dominant
cost is in their *frequency over a long production lifetime*, not their
share of any single 5-minute window), so their fix shows up as a p99
tail-latency and buffer-efficiency improvement (see table in §0) and as a
large *relative* per-call improvement, not as a further drop in the
already-small overall CPU percentage. The headline PostgreSQL-saturation fix
remains the chat RLS correction (§5.1 / the referenced prior report).

**Index storage cost**: three new indexes, all on tables in the tens-of-
thousands-of-rows range in this deployment; no measurement of absolute disk
bytes was taken (not requested as a hard gate, and the relative sizes are
self-evidently small compared to the already-growing `chat_conversations`/
`consultation_trace_events` tables they sit beside) — disclosed as
NOT MEASURED precisely rather than asserted negligible without a number.
